# 雙向審查與集中修補

## Reviewer 任務

輸入：使用者要求／範圍、目前文件、共用證據（若有）、來源根目錄、run.json 與其 snapshot_sha256。
輸出只寫 `REVIEW.md`；不得編輯 Maker 文件或 run.json。若執行工具不可用，要求主代理提供實際指紋檢查結果，明確記錄核對方式。

1. 先檢查快照對應目前檔案。自行讀原始碼；以 Maker 的範圍清單作導航，不能以它作為唯一覆蓋清單。
2. **文件 → 來源**：核對範圍內全部可驗證主張，包括圖、表、範例與附錄。相同事實合併查一次，但列出全部受影響位置。區分實作、核准需求、提案、推論。
3. **來源／需求 → 文件**：獨立枚舉可達分支、失敗／空值／未命中、欄位契約、狀態及副作用，與文件覆蓋表比對。需求缺失不因「沒有程式碼」而消失，應標現況差異。
4. 查UI操作／狀態覆蓋、必要執行證據與圖片需求；依 [執行期驗證](runtime-verification.md) 分別判斷。
5. 每個問題有穩定 ID、影響、來源、所有文件位置與具體修法。先全掃再交出完整結果，不抽樣、不要求至少找出幾個缺陷，不發出暫定 PASS。

大範圍可依來源群組分批檢查並留下已查範圍，仍在同一連續工作流程完成；未檢查部分要列出，不能因上下文限制宣稱全部通過。

## 哪些問題阻擋

- 錯誤入口、資料來源、核心行為／交易／權限／對外契約，或任何會誤導實作／驗收的重要錯誤。
- 本次必須覆蓋的要求或重要正常／例外行為缺漏。
- 把推論當事實、把 simulation 當真實驗證，或重要主張無足夠證據。
- 審查期間檔案變動，或必要執行／交付證據缺失。

不影響本次使用目的的文句改善與額外背景只是非阻擋建議；不擴大需求。數字／字數規則若未定義計數方式，列一次規則歧義，不自行每輪換標準。

## 修補

Maker 先讀完整問題集合，查清來源與所有受影響位置，再批次修正。每個檔案集中寫入，避免逐句來回覆寫；允許必要的相依調整，但不新增無關場景或設計。
發現無法解決的阻擋項時，繼續完成不依賴它的修正並如實記錄未完成部分，不宣稱整批成功。
實際重讀每個修補位置，再建立新快照。Reviewer 做完整雙向複審，區分剩餘問題為「未修好／修補引入／上輪漏查／範圍改變」。
預設一次集中修補；第二次審查仍有阻擋項時結束自動迴圈。記錄已修、待解與改策略建議，不能用減少缺陷數或高分掩蓋重大錯誤。
中途平台中斷不消耗一次修補；續跑完成同一問題集合，不重置成另一輪。

## 最小 REVIEW.md

```markdown
# Review
- review_kind: independent | self
- verdict: pass | fail | incomplete
- reviewed_revision: 整數
- reviewed_snapshot_sha256: 審查輸入的指紋
- reviewed_files: 文件清單
- 文件→來源：已核對的主張／來源群組與未查部分
- 來源／需求→文件：已核對的行為／要求與未查部分
- runtime_evidence: static | observed | simulation | missing（按項目列）

| ID | 阻擋？ | 問題與影響 | 來源證據 | 全部文件位置 | 修法／關閉證據 |
|---|---|---|---|---|---|

## 限制與非阻擋建議
```

無問題就記「無」，不補空殼問題。若需要 diff_rate，分母使用去重後實際核對項目並說明覆蓋邊界；不能以添加正確的小項目稀釋重要缺陷。
