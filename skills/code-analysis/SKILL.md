# Code Analysis

以「範圍 → 來源證據與行為清單 → 文件 → 獨立雙向審查 → 集中修正 → 交付」執行分析。
不做逐階段數字評分；以具體缺陷、需求覆蓋與證據決定完成。

## 連續執行與成本原則

- 從目前步驟自動接到下一步，直到交付。不因階段完成、保存 checkpoint 或審查通過要求「是否繼續」，不強制換 session。
- 預設一個 Maker（目前主代理）＋一個獨立 Reviewer；不為各分析方法建立獨立代理。一次完整審查，只有發現需要修補的問題才再審查。
- 相同來源在同一版本內按路徑／符號去重讀取；同一事實供多個章節共用。Reviewer 仍需自行核對來源，不能拿 Maker 的結論當查證。
- 預設只產出使用者需要的文件、`REVIEW.md` 與一份 `run.json`。範圍與證據放文件短附錄；多份文件需要共用時才拆出 `EVIDENCE.md`。
- 不為省資源而漏查必要分支，也不建立全專案索引、固定分數表、每階段 handoff 或無需求的 Mock。
- 平台中斷或必要資訊缺失仍可能阻擋；按 [執行與續跑](references/execution.md) 保存進度。規則不宣稱能防止平台故障。

## 使用邊界

- 本 skill 自成一套流程，不需要舊版分析 skills、特定 plugin、專案記憶庫或命名好的 agents。
- 只有一套分析流程，依使用者需要的交付物決定分析方法與文件份數；不設快速／完整模式，不沿用舊流程的 gate／schema 宣告通過。
- 以使用者本次要求與專案有效規範決定範圍；已確認的入口、交付格式與授權沿用，不重複詢問。
- 分析不隱含修改產品程式碼、提出 TO-BE 設計、發布或覆寫外部文件。使用者已要求的文件修正直接執行。
- Claude／Codex 使用各自可用的讀檔、搜尋、執行及代理工具；不把某平台的工具名稱當成必要 API。支援方式見 [執行與續跑](references/execution.md)。

## 1. 定位目標與交付要求

讀專案指引、`.analysis-profile.md`（若有）及本次提供的需求／截圖。記憶或既有文件用來導航；AS-IS 事實仍核對目前來源，需求與現況分開標示。

缺 profile 時，從建置檔、路由／工作定義及目錄辨識必要資訊即可，不強制先完成訪談或另建 profile。
確認實際入口與有限範圍；有截圖或錯誤訊息時先看，再追碼。不要從票號摘要、套件名稱或目錄名稱直接推定業務入口。

將目標、入口、來源根目錄、範圍、輸出、必須覆蓋的要求記在分析文件的範圍段落；有外部 SCOPE／契約時直接引用，不再複製。
僅在入口有歧義、需求衝突或必須擴大範圍時提出具體問題；可獨立完成的部分繼續。

| 使用者意圖 | 執行方式 |
|---|---|
| 分析功能或指定文件 | 依輸出要求直接產出；未提供模板時，從已表達需求建立最小交付清單並說明採用的格式 |
| 要求多份文件、AS-IS 基線 | 用共用證據產出指定文件；見 [文件選擇](references/deliverables.md) |
| 驗證既有文件 | 直接進入雙向審查，不重跑文件生成；只要求驗證時交付問題清單，不自動改原文件 |
| 續跑 | 先按 [執行與續跑](references/execution.md) 核對檔案與已完成檢查 |
| 排版、圖表配置或轉檔 | 檢查呈現與內容一致性；確認未改語意後，不重跑技術分析 |

未指定文件格式時，採一份整合分析並說明假設。範圍大小與文件份數分開判斷，不因涉及 API／跨系統就自動擴寫文件或重跑。

## 2. 先建來源證據與行為清單

讀 [分析方法](references/analysis-methods.md)，只執行與本次交付相關的方法。
從入口追到分支、資料、交易及外部邊界，先確認執行流程，再推導業務規則。

用 [分析模板](assets/analysis.template.md) 的證據與覆蓋表記錄以下內容；共用多份文件時才抽出 `EVIDENCE.md`：

- **來源**：真實路徑＋符號／行號，記錄來源版本；同一事實只維護一份，文件引用穩定 ID。
- **主張**：區分 `code-derived`、`inferred`、`business-input`；另標 AS-IS／approved-requirement／proposed。
- **行為清單**：由原始碼與範圍內需求獨立枚舉觸發條件、正常／失敗分支、狀態改變、副作用，再映射到文件。
- **未知**：記錄缺少什麼、影響哪個要求、是否阻擋交付；不要填入未查證的猜測作為事實。

只查到某個入口不呼叫某段邏輯，不能推廣成整個系統都不使用。條件可查時描述各分支；外部套件可查契約時先查契約，不把「沒有實作 repo」等同完全不可知。

## 3. 產出文件

按 [文件選擇](references/deliverables.md) 面向讀者撰寫，沿用使用者模板。
分析方法不必各自產生獨立中間文件。需要多份文件時引用同一證據，不從另一份摘要重建 SQL、條件或交易邏輯。

重要入口／資料來源／主流程尚未確定時，暫停依賴該結論的文件，列出具體缺口。可由來源解決的錯誤直接查清，不因分數、固定搜尋次數或一般格式問題要求人工決策。

UI 狀態覆蓋與實際執行證據分開處理，按 [執行期驗證](references/runtime-verification.md) 判定。Mock／重建畫面只能標 `simulation`。

## 4. 一次獨立雙向審查

讀 [審查與修補](references/review-and-repair.md)。當環境提供且允許子代理時，使用**一個獨立 Reviewer 子代理**：
給它範圍、輸出要求、當前文件／證據、原始碼位置及該參考文件；要求同時查文件→來源與來源／需求→文件。
Reviewer 不編輯 Maker 文件，不預先接受 Maker 的結論。不要把每個 collector 都拆成 agent。

沒有獨立代理或其執行不被允許時，完成可做的自查，明確標 `self_reviewed`；不得冒充獨立 PASS。若本次交付要求獨立審查，狀態為 `review_pending`。

審查前使用 [檔案快照工具](references/execution.md#檔案快照) 記錄來源、範圍、文件與證據的指紋，Reviewer 在 `REVIEW.md` 引用該次 `run.json` 的 `snapshot_sha256` 與 revision。
Node.js 不可用時可用其他可用 SHA-256 工具與人工紀錄完成同等核對；需揭露缺少自動鎖定與續跑檢查，不能因輔助工具缺失停止原本可做的分析。

## 5. 集中修正並核對

將完整發現集合一次交給 Maker，預設允許一次集中修補。只修發現及其必要相依內容；新增／改寫主張均需證據。
修補後重新讀取實際檔案、生成新快照，再由獨立 Reviewer 做完整雙向複審，確認舊問題已關閉及新問題的來源。
複審仍有阻擋問題時停止同一自動修補迴圈，交付具體問題與建議；使用者明確要求延伸調查時，可改策略繼續，不重複同一無效迴圈。非阻擋改善建議不引發新一輪。

## 6. 交付判定

- `verified`：獨立雙向審查完成、當前指紋一致、必須覆蓋的內容齊全、無未解阻擋缺陷，必要執行證據已取得。
- `self_reviewed`：已完成自查但無獨立審查；可交付草稿，不能稱獨立驗證完成。
- `review_pending`：等待必要審查；`blocked`：缺少影響正確性／交付要求的來源或執行證據。
- 使用者接受的偏差記為 `accepted_with_exceptions`，附接受範圍；不得改稱無缺陷通過。

摘要提供文件位置、已覆蓋範圍、審查方式、未解事項及執行證據限制。交付物與審查指紋最後再核對一次。
`diff_rate` 僅在需要比較時報告並說明分母，不作單一放行條件。已發布與已審查是不同狀態，只有使用者要求發布時才核對發布位置。
